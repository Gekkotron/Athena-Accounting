# Rule-driven auto-splits — design

**Status:** proposed
**Date:** 2026-09-16

## Problem

Athena's rule engine (`backend/src/domain/rules/`) stamps exactly one
category on each matched transaction — `rules.category_id` is
`NOT NULL` and the engine emits a single `UPDATE transactions SET
category_id = ?, category_source = 'auto'` per match. Users who want
a recurring merchant to be ventilated across several categories have
only two options today, both bad:

- Live with a single category and lose granularity in reports.
- Split every matching transaction by hand (`PUT
  /api/transactions/:id/splits`) — accurate but tedious, and any
  future import for the same merchant restarts the manual work.

The most common case that motivates this is **mixed retailers**: a
70% books / 30% electronics split on Amazon, a 60% groceries / 40%
household split on Carrefour Market, a 50% work meals / 50%
entertainment split on a business-and-personal restaurant tab. The
right shape is a rule that, when it matches, produces N splits
automatically at pre-declared percentages.

`backend/src/domain/imports/` already runs a per-row category apply
step at import time (`categorizeOne` in
`backend/src/domain/rules/recategorize.ts:114`) and a bulk
`recategorizeAll` for the "Regenerate categories" button
(`recategorizeAll` at line 50). Both need to learn how to emit split
rows in addition to (or instead of) the single-category UPDATE, while
never overwriting a user's manual work.

## Non-goals

- **Amount splits** (a fixed 15 € to *Frais bancaires*, the rest to
  *Courses*). Percentages compose more predictably across amounts —
  the same rule applies to a 12 € cash withdrawal and a 300 €
  weekly shop. Amount splits would also need their own conflict
  rules for over-total shortfalls. Track as a v1.1 idea, not
  in-scope here.
- **Cascading rules** (rule A produces a split, then rule B
  re-splits one of the child categories). Explicit non-goal —
  splits generated by the engine are terminal, and no rule re-runs
  on split rows.
- **Amount-conditional splits** (different percentages above / below
  a threshold). Same "compose across the range" argument — a
  percentage set is one rule.
- **Regenerate-on-rate-change**. Once splits are emitted for a
  transaction, changing the rule's percentages after the fact does
  *not* automatically retroactively re-split existing transactions.
  Users hit **Réappliquer les règles** for that (existing flow) —
  the engine then respects the auto/manual distinction the same way
  it does today for single-category rules.
- **Multi-currency split rules.** Percentages are dimensionless, so
  this is a non-issue at the rule level. The split rows land in the
  parent's currency (existing `transaction_splits` invariant),
  reported through the FX consolidation path that shipped in
  migration 0038 — no change needed here.

## Decision

Introduce a small companion table `rule_splits(rule_id, category_id,
percent, position)` that hangs off `rules` via `ON DELETE CASCADE`.
Presence of one or more `rule_splits` rows for a given rule flips
that rule from single-category mode to split mode. In split mode,
the engine emits `transaction_splits` for each matched transaction
(one row per `rule_splits` entry, amounts computed in cents from
the parent's amount × percent / 100 with the last row taking the
remainder so the sum invariant holds exactly). Otherwise the engine
behaves exactly as today.

The rule keeps its existing `category_id` NOT NULL — for split-mode
rules it becomes the **primary / display category** (the one shown
in listings, reports that don't drill into splits, and the "top-level"
category assigned to the parent transaction so single-category
filters still find the row). Percentages sum to exactly 100, enforced
by a deferrable trigger mirroring the existing
`transaction_splits_checksum` pattern from migration 0014.

Conflict handling with user work is expressed through a new
`transactions.splits_source` enum column
(reusing `categorySourceEnum` — `'auto' | 'manual' | 'default' | 'llm'`),
set to `'manual'` by `PUT /api/transactions/:id/splits` and to
`'auto'` by the rule engine. The engine's skip rule becomes:

- **Skip** if the transaction has `splits_source = 'manual'` (user
  edited splits by hand — never overwrite, regardless of the
  `preserveManual` flag).
- **Skip** if the transaction has `category_source = 'manual'` and
  `preserveManual = true` (existing behaviour for single-category
  rules extends unchanged).
- **Re-emit** if the transaction has `splits_source = 'auto'` (the
  engine put those splits there previously, safe to regenerate from
  the current rule set).
- **Emit fresh** otherwise (no existing splits, or splits at
  `'default'`).

Rationale — an independent `splits_source` column rather than
overloading `category_source`: the two lifecycles are actually
independent. A user can accept an auto-emitted split, then manually
re-tag the single "primary category" on the parent transaction row
(without touching the splits themselves) — that action bumps
`category_source` to `'manual'` but leaves `splits_source` as
`'auto'`. Conflating them would either over-preserve or
under-preserve. One extra column is a cheap price for correctness.

## Behavior

### Rule form (`Rules` page)

- The existing "Category" picker gets a second, adjacent mode
  toggle: **Ventilation multi-catégories** (checkbox). Off = today's
  single-category behaviour, unchanged. On = the single picker is
  replaced by a two-column list: category on the left, percentage
  input on the right (0–100, integer only), with `+ Ajouter une
  catégorie` and per-row `×` remove.
- A live sum indicator ("Somme: 100 %") turns amber when != 100 and
  the submit button disables until valid.
- Minimum 2 rows, maximum 20 (mirrors the `transaction_splits`
  bounds).
- On save the frontend POSTs `/api/rules` with an optional
  `splits: [{ categoryId, percent }]` array. When present, the
  backend creates the rule + `rule_splits` rows atomically. The
  rule's own `categoryId` field is the first row's category by
  convention (the "primary"). When absent, everything works as
  today.

### Rule listing

- Split-mode rules render the primary category with a small `+N`
  badge indicating the number of extra splits, and expand on hover
  / focus to show the full breakdown. Non-split rules render
  unchanged.
- The Rules `FlatTable` / `GroupedView` respect the same shape —
  the extra column data comes from the same `GET /api/rules`
  response with a new `splits: [{ categoryId, percent }]` array
  hydrated per rule.

### Import-time application (`categorizeOne`)

Change signature so it can emit splits:

```ts
// current
async function categorizeOne(
  compiled, defaultId, txId, amount, normalizedLabel,
): Promise<{ categoryId: number | null; source: 'auto' | 'default' }>

// proposed
async function categorizeOne(
  compiled, defaultId, txId, amount, normalizedLabel, tx?: Runner,
): Promise<{
  categoryId: number | null;
  source: 'auto' | 'default';
  emittedSplits?: number; // count of split rows written, 0 or ≥ 2
}>
```

When the matched rule has `rule_splits`, the function runs, inside
the caller's outer transaction:

1. Skip if `EXISTS (SELECT 1 FROM transaction_splits WHERE
   transaction_id = txId)` — an import-time transaction shouldn't
   have splits yet, but be defensive.
2. Compute per-row cents:
   ```ts
   const parentCents = Math.round(Number(amount) * 100);
   const cents = splits.map(s => Math.round(parentCents * s.percent / 100));
   const drift = parentCents - cents.reduce((a, b) => a + b, 0);
   cents[cents.length - 1] += drift; // last-row absorbs rounding
   ```
3. Insert `transaction_splits` rows in one multi-values `INSERT`.
4. UPDATE the parent's `category_id = rule.category_id`,
   `category_source = 'auto'`, `splits_source = 'auto'`.

The deferred sum trigger from migration 0014 validates step 3 at
commit; the last-row-absorbs-drift guarantees exact equality.

### Bulk application (`recategorizeAll`)

Rewritten around the same primitives. The pass builds three sets:

- `singleUpdates`: `Map<categoryId, number[]>` — same as today, for
  single-category rule hits and default fallbacks.
- `splitEmits`: `Map<ruleId, number[]>` — transactions that should
  receive a fresh split from `ruleId`.
- `preserved`: count of skipped rows.

For each transaction, the decision tree runs:

```
if splits_source='manual':                → preserved++
elif category_source='manual' and preserveManual:
    if no splits: → preserved++
    else: → preserved++   (belt-and-suspenders)
else:
    hit = firstMatch(compiled, label, amount)
    if hit and rule_splits(hit).length ≥ 2:
        splitEmits[hit.rule.id].push(tx.id)
    elif hit:
        singleUpdates[hit.rule.categoryId].push(tx.id)
    else:
        defaultBucket.push(tx.id)
```

Flush strategy:

- `singleUpdates` and `defaultBucket` flush with the existing
  batched-IN-list `UPDATE` (unchanged).
- `splitEmits` flushes per (`ruleId`, batch of tx ids):
  1. `DELETE FROM transaction_splits WHERE transaction_id IN (...)`
     — clears any prior auto-generated splits (safe: we established
     `splits_source != 'manual'` above).
  2. One multi-values `INSERT INTO transaction_splits` with all
     rows for all txs in this batch, cent amounts pre-computed in
     JS with the drift-adjustment above.
  3. One batched `UPDATE transactions SET category_id = rule.category_id,
     category_source = 'auto', splits_source = 'auto' WHERE id IN
     (...)`.

Ordering matters — the trigger is `DEFERRABLE INITIALLY DEFERRED`,
so both DELETE and INSERT commit atomically at end-of-transaction,
which is exactly the check we need.

### Manual splits path (`PUT /api/transactions/:id/splits`)

One-line change: set `splits_source = 'manual'` on the parent as
part of the same transaction that replaces the split rows. Existing
route body already runs a `db.transaction` — add the parent UPDATE
before returning.

`DELETE /api/transactions/:id/splits` clears both the child rows
AND `splits_source` (back to NULL, so a re-import can re-emit).

## Backend

### Schema — migration `0042_rule_splits.sql`

Two schema changes plus one trigger:

```sql
-- 1. rule_splits companion table.
CREATE TABLE rule_splits (
  id          SERIAL PRIMARY KEY,
  rule_id     INTEGER NOT NULL REFERENCES rules(id) ON DELETE CASCADE,
  category_id INTEGER REFERENCES categories(id) ON DELETE SET NULL,
  percent     INTEGER NOT NULL CHECK (percent BETWEEN 1 AND 99),
  position    INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX rule_splits_rule_idx ON rule_splits (rule_id);

-- 2. transactions.splits_source. NULL = no splits (or splits cleared);
--    non-NULL = the split set has a known origin.
ALTER TABLE transactions
  ADD COLUMN splits_source category_source;

-- 3. Sum-guard trigger mirrors transaction_splits_checksum.
CREATE OR REPLACE FUNCTION rule_splits_percent_checksum()
RETURNS TRIGGER LANGUAGE plpgsql AS $$
DECLARE
  rid   INTEGER;
  total INTEGER;
BEGIN
  rid := COALESCE(NEW.rule_id, OLD.rule_id);
  SELECT COALESCE(SUM(percent), 0) INTO total
    FROM rule_splits WHERE rule_id = rid;
  -- Zero rows is legal (rule reverts to single-category mode).
  IF total <> 0 AND total <> 100 THEN
    RAISE EXCEPTION 'rule_splits percents must sum to 100 (rule_id=%)', rid
      USING ERRCODE = 'check_violation';
  END IF;
  RETURN NULL;
END $$;

CREATE CONSTRAINT TRIGGER rule_splits_percent_checksum_trg
  AFTER INSERT OR UPDATE OR DELETE ON rule_splits
  DEFERRABLE INITIALLY DEFERRED
  FOR EACH ROW EXECUTE FUNCTION rule_splits_percent_checksum();
```

Drizzle mirror in `backend/src/db/schema.ts` — add `ruleSplits` next
to `rules`, add `splitsSource` on `transactions`.

### Routes

- `GET /api/rules` — response gains `splits: [{ categoryId,
  percent }]` per rule (empty array when the rule is
  single-category). Fetched via a `LEFT JOIN` grouped by rule_id
  or a `Promise.all` per rule (small N, prefer JOIN + one grouping
  pass in JS).
- `POST /api/rules` — body gains optional `splits:
  z.array(z.object({ categoryId: z.number().int().positive(),
  percent: z.number().int().min(1).max(99) })).min(2).max(20).optional()`.
  Validation: when present, sum of percents must equal 100; every
  categoryId must be owned by the caller (same enumeration-safe
  check as the splits route). Rule row + rule_splits rows written
  in one transaction. When absent, current single-category flow
  unchanged.
- `PUT /api/rules/:id` — body's `splits` field, when present,
  atomically replaces the current `rule_splits` set. `null` (or an
  empty array) reverts the rule to single-category mode (DELETE the
  rows; the trigger accepts total=0). Absent = leave untouched.
- `DELETE /api/rules/:id` — `ON DELETE CASCADE` handles rule_splits;
  no code change.
- `POST /api/recategorize` — unchanged externally; the engine
  behaviour above kicks in when any active rule has rule_splits
  rows. Response gains `splitsEmitted` count next to `recategorized`
  for the summary UI.
- `POST /api/rules/preview` — unchanged (preview is about "would
  this rule match?", not "would it split correctly"). The frontend
  already renders the target category from the preview response;
  split-mode preview will lean on the rule form's live percent
  sum + the client-side ventilation math to render an example.

### Engine — `backend/src/domain/rules/`

- Extend `Rule` (from `matcher.ts`) with `splits: Array<{
  categoryId, percent }>` — hydrated at load time by
  `loadCompiledRules` in `recategorize.ts` via a `LEFT JOIN
  rule_splits` (one query, then a per-rule group).
- Add a pure `computeSplitCents(parentCents, percents: number[]):
  number[]` helper — the last-row-absorbs-drift math. Test it in
  isolation.
- `categorizeOne` and `recategorizeAll` follow the pseudo-code from
  the Behavior section above.

### Backup

`backend/src/http/routes/backup/schema.ts` — the `rules[]` entry
shape gains optional `splits: z.array(z.object({ category:
z.string(), percent: z.number().int() })).optional()`. Natural key
still `(keyword, category)` on the parent rule; the child splits are
restored in order with `position` reflecting array index. Existing
backups without the field restore unchanged (the array is optional).

`dump.ts` / restore path — extend to walk the new child rows and
re-resolve categories by name during restore. Rules whose split
categories don't all resolve for the target user are dropped whole
(don't silently drop just one split — the sum wouldn't be 100), and
reported in the skipped-rules count with a distinct reason string.

### Migration ordering

Migration `0042_rule_splits.sql` runs after 0041 (TOTP). Zero downtime:
- New column `splits_source` is nullable and defaults to NULL — no
  backfill required, existing rows keep behaving as before.
- New table `rule_splits` starts empty — no existing rule is
  affected.

## Threat model / edge cases

- **A user manually edits one split of an auto-generated set**
  (via `PUT /api/transactions/:id/splits`) — the whole set flips to
  `splits_source = 'manual'` and is preserved from then on. The
  user can force a re-emission by clearing the splits and
  re-applying rules, matching the existing pattern for
  categorization.
- **A split rule matches, but the parent already has an internal
  transfer group** (`transfer_group_id IS NOT NULL`). The engine
  already filters `WHERE transfer_group_id IS NULL` in
  `recategorizeAll`, so transfers never receive splits — same
  invariant applies.
- **Category deletion mid-flight.** `rule_splits.category_id ON
  DELETE SET NULL` matches the parent `rules.category_id` behaviour.
  A split with a null category is a valid "uncategorized" slice —
  the engine still emits the slice, the UI renders it as `Non
  catégorisé`, and the sum invariant still holds. The rules page
  surfaces such rules with a "catégorie manquante" warning so the
  user can fix them.
- **User bumps `rules.category_id`** (the "primary" for a
  split-mode rule) via `PUT /api/rules/:id` but doesn't touch
  `splits`. Behaviour: the primary changes on the parent
  transaction on next re-application, but the split rows keep the
  categories the user picked in the editor. This is the correct
  read — the primary is a display convenience, not a source of
  truth for the ventilation.
- **Sum of percents is legal on POST but the trigger fires on
  DELETE** (all rows removed → total=0). The trigger explicitly
  accepts 0 as "no splits" — reverting to single-category mode is
  not an error.
- **A rule with 20 splits × a batch of 5000 imported transactions**:
  100 000 split rows inserted in one multi-values INSERT. That's
  well within Postgres and PGlite limits, but the request body of
  a `POST /api/imports` is bounded elsewhere (`fastify-multipart`
  cap) so we should assert the batch stays chunked at
  `BATCH = 500` transactions × 20 splits = 10 000 rows per
  round-trip, and iterate. Matches the pattern already used by the
  bulk UPDATE batches.
